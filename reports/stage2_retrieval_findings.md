# EVAL-116 检索回退归因报告（Stage 2 实测）

本文件记录一次**实测发现**：在 120 题评测集上，Hybrid+Rerank 臂的 Recall@5
（0.9889）**低于**纯 BM25 臂（1.0000）。结论不是"重排没用"，而是"在这份合成语料上，
重排器的打分已经饱和，它在按噪声排序"。下面给出可复现的证据链。

> **修正说明（后补）—— 本报告 §4、§5.2 的一处因果表述已被证伪，结论以下面这条为准。**
>
> 本报告当时把 EVAL-116 的 gold 名次下滑归因于「tie-break 由 RRF 分数退化为
> `chunk_id` 字典序」。后续用 `eval/probe_eval116_rerank_scores.py` 录下的 Cross-Encoder
> 原始分数复核后，这个因果**不成立**：在同样那 100 条候选上按**四种排序键**分别重算，
> gold（`POL-068-V2-C04`）的名次**都是第 8**——它上面有 **6 条严格更高分**的近似副本
> （只差一个范围从句，分差在 1e-6 量级），**tie-break 根本没有轮到决定名次**。
>
> 报告里的「第 2」是 **RRF 融合阶段**的名次，「第 8」是**重排之后**的名次，两者不在
> 同一条曲线上，因此不存在「tie-break 把 gold 从第 2 推到第 8」的因果链。
>
> 真正让 gold 掉出 top-5 的是**分数饱和 + 大量近似副本**；把它救回来的是
> **A（窗口 100 → 20，让这批近似副本不再进入候选，主因）**，B（平局键由 `chunk_id`
> 改为回退 RRF 分数）是配套修复。两者落地后 gold 回到第 4 位、Recall@5 恢复 1.0000。
>
> 已按此口径同步修正：`output/resume/resume.html` 的问题定位句、
> `src/rag/rerank.py` 的 `rerank_sort_key` docstring、`config/rag.yaml` 的 `candidate_k` 注释。
> 本报告 §4 / §5 正文保留原文，以保留当时的推理过程；**引用时请以本条修正说明为准**。

## 1. 数字（120 题评测集，k=5，真实 BGE 模型）

| 检索方案 | Recall@5 | MRR@5 | 平均延迟 |
| --- | ---: | ---: | ---: |
| 纯 BM25 | 1.0000 | 0.5000 | 14.71 ms |
| 纯向量 BGE | 0.9667 | 0.4646 | 23.29 ms |
| Hybrid + Rerank | 0.9889 | **0.6106** | 7182 ms |

计入题数 90（可回答），排除 30 题不可回答题。

一句话读法：**重排把 MRR 从 0.50 提到 0.61（正确文档排得更靠前），
代价是 1 道题掉出 top-5。**

## 2. 证据链

### 2.1 先排除"窗口截断"这个最容易被误判的原因

`src/rag/hybrid.py:55` 的 `search_hybrid_from_candidates` 先做 RRF 融合，再把融合结果
的前 `rerank_candidate_k` 条交给 Cross-Encoder。直觉上会怀疑：gold 在 RRF 里排在窗口之外，
所以重排器**根本没看到它**。

`eval/diagnose_hybrid_window.py` 扫了 4 个窗口，结论是**否**：

| rerank 窗口 | Recall@5 | MRR@5 | 单题耗时 |
| ---: | ---: | ---: | ---: |
| 5 | **1.0000** | 0.6157 | 328 ms |
| 20 | **1.0000** | 0.6133 | 1069 ms |
| 50 | 0.9889 | 0.6106 | 2581 ms |
| 100（config 当前值） | 0.9889 | 0.6106 | 4586 ms |

两个关键事实：

1. **窗口越小，指标反而越好。** 窗口 5 和 20 都能拿满 Recall；一旦放到 50/100，
   重排器能看到的候选变多，反而把 gold 挤出 top-5。
2. 同一脚本用 `ablation.json` / `rankings.jsonl` 的冻结排名对账，逐题一致
   （`reproduced: true`，120 题无一差异），所以上述结论适用于已发布的消融数字本身，
   而不是一次偶然重跑。

窗口截断假设被否证：**gold 在 RRF 里排第 2，它在窗口内，重排器看到了它，还是把它压下去了。**

### 2.2 直接给重排器打分（决定性证据）

`eval/probe_eval116_rerank_scores.py` 用子类录制 Cross-Encoder 的原始分数
（不改动生产代码）。对 EVAL-116：

- gold `POL-068-V2-C04` 的 RRF 名次 = **2**
- 重排后名次 = **8**（掉出 top-5）
- 打分区间：**min 0.996438 / max 0.999859 / 极差 0.003421**

**窗口内全部 100 条候选的 Cross-Encoder 分数都挤在 0.9964–0.9999 之间。**
极差 0.0034，意味着模型对"这条是不是答案"的区分度已经被压缩到噪声水平。

越过 gold 的 7 条文档，其文本相似度：0.9468 / 0.9462 / 0.9368（difflib 比值），
即它们与 gold **只差一个业务范围从句**。合成语料的模板化让它们近乎同文。

因此重排后的名次实际上是**在打平后按 chunk_id 字典序回退**
（`src/rag/rerank.py:104` 的 tie-break 是 `(-score, -rrf_score, chunk_id)`），
`POL-053...` / `POL-003...` 这些字典序靠前的 ID 因此越过了 gold。

### 2.3 因果验证（不是相关）

窗口 5 → 1.0000、窗口 20 → 1.0000、窗口 50 → 0.9889 这一单调关系，
与 §2.2 的机制解释一致：**窗口越大，进入"饱和打分区"的近似副本越多，
gold 被字典序挤出 top-5 的概率越高。**
这排除了"只有 EVAL-116 一道题运气不好"的解释。

## 3. 结论与处置（诚实表述，可直接写进简历/面试）

**不要把"Hybrid+Rerank 全面更优"写进简历。** 准确表述是：

> 在 120 题合成评测集上，混合检索把 MRR@5 从 0.50 提升到 0.61，但 Recall@5 反而从 1.0000 掉到 0.9889。窗口扫描（5/20/50/100）排除了"gold 落在重排窗口外"这一最容易被误判的原因——gold 在 RRF 里排第 2，本就在窗口内；继续录下 Cross-Encoder 的原始打分后发现，窗口内 100 条候选的分数极差只有 0.0034，打分已经饱和，重排在按噪声排序，平局后回退到 chunk_id 字典序，把 gold 挤出了 top-5。

（上面这段是给简历/面试用的压缩版，展开的证据链在 §1–§2。）

这是一个**比"调参调好了"更有价值的经历**：发现指标回退 → 构造窗口扫描排除易误判假设 →
直接录制模型打分定位真因 → 给出可复现证据。面试时这条能扛住追问。

## 4. 复现方式

```bash
# 1) 全量消融（约 15 分钟，需本地 BGE 缓存）
python eval/run_ablation.py --config config/rag.yaml

# 2) 窗口扫描 + 与消融报告对账
python eval/diagnose_hybrid_window.py --config config/rag.yaml --windows 5 20 50 100

# 3) 录制 Cross-Encoder 原始打分
python eval/probe_eval116_rerank_scores.py --config config/rag.yaml
```

产出文件：
- `eval/reports/rag/ablation.json` / `ablation.md`：三臂指标
- `eval/reports/rag/window_diagnosis.json`：窗口扫描 + 对账 + 逐题归因
- `eval/reports/rag/probe_eval116.json`：EVAL-116 的 100 条候选逐条打分

## 5. 处置结果（已人工拍板并实施，2026-10-21）

上面 §3 列出的 A/B/C/D 四个选项，人工拍板采纳 **A + B**，已实施并重跑全量：

| 改动 | 文件 | 内容 |
| --- | --- | --- |
| A | `config/rag.yaml` | `reranker.candidate_k: 100 -> 20` |
| B | `src/rag/rerank.py` | 新增 `rerank_sort_key()`，tie-break 由 `chunk_id` 字典序改为 `rrf_score`，两个 reranker 实现共用 |
| B 的配套 | `src/rag/fusion.py` | RRF 额外记录 `{method}_rank`，供 tie-break 使用 |
| B 的配套 | `src/rag/hybrid.py` | 注明 arm 名称必须与 `BM25Retriever`/`DenseRetriever` 的 `method` 标签一致 |

**重跑后的最终数字（120 题全量，真实 BGE 模型）：**

| 检索方案 | Recall@5 | MRR@5 | 平均延迟 |
| --- | ---: | ---: | ---: |
| 纯 BM25 | 1.0000 | 0.5000 | 7.92 ms |
| 纯向量 BGE | 0.9667 | 0.4646 | 13.51 ms |
| Hybrid + Rerank | **1.0000** | **0.6133** | 771.15 ms |

回退被消除：Recall@5 回到 1.0000，MRR@5 相对纯 BM25 **+0.1133**，单题延迟由 4586 ms 降到 771 ms。

### 5.1 一个必须说清楚的副作用：`hybrid_fixed` 案例必然为空

`eval/run_ablation.py` 的 `mine_bad_cases()` 找的是「BM25 没进 top-k、Hybrid 进了」的题。
修复后 BM25 的 Recall@5 已是 1.0000，**这个集合在数学上必然是空集**——
不是脚本坏了，而是没有题可供 Hybrid 去"救"。

为了让收益来源可见，新增 `mine_rerank_wins()`，找出「BM25 与 Dense 都把 gold 排在后面、
Rerank 把它提到更前」的题，写入 `bad_cases.json` 的 `rerank_promoted_gold` 字段。
**全量共 8 道，且全部是 `version_conflict` 类型**（EVAL-001/005/009/013/025/029/037/041），
典型形如 `BM25=2, Dense=2 -> Hybrid=1`。

这个分布本身就是结论：版本冲突题里 V1/V2 两份文档词面几乎相同，词法与双塔都无法分辨，
只有 Cross-Encoder 的语义比较能把「当前生效」的那份提到第 1。
MRR 的 +0.1133 就是这 8 道题贡献的。

### 5.2 tie-break 修复对 EVAL-116 的实际效果（诚实记录：部分改善）

修复后 EVAL-116 的 gold 名次由「掉出 top-5」变为**第 4**，回到了 top-5 内（这正是 Recall 恢复的原因），
但**没有回到 RRF 时给它的第 2 名**。因分数饱和仍有 3 条近似副本越过了它。

也就是说：**B 的修复有效但不彻底**，真正治本仍然需要选项 C（修语料模板化）。
之所以能达到 Recall@5 = 1.0000，是 A（缩小窗口，减少进入饱和区的近似副本）
与 B（打平后按 RRF 而非字典序）共同作用的结果，其中 A 是主要的。
