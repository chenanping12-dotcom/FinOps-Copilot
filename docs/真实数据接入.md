# 真实数据接入（Real Data Onboarding）

> 目标：让 FinOps-Copilot 的计算口径**在一份真实公开的电商交易数据上跑一遍**，
> 并诚实记录「合成数据 vs 真实数据」的差异。本页只讲**怎么复跑**与**口径边界**；
> 结论见 [`reports/real_data_findings.md`](../reports/real_data_findings.md)。

## 1. 为什么需要这条链路

项目此前所有数据都是合成的（`config/data_spec.yaml: synthetic_only: true`），
六类脏数据按 1% 均匀注入。合成数据的「脏」是**人造缺陷**，而真实数据的「脏」是
**业务结构性缺失**（例如四分之一的订单根本没有客户号）。这两种脏对口径的压力完全不同，
所以必须真接一次真实数据。

本链路的设计原则：

1. **不编造**：下载失败就报错并打印试过的 URL，不做 mock、不抽样伪造。
2. **不改 Stage 1 产物**：真实数据进 `data/processed/real_orders.db`，
   绝不触碰 `data/generated/orders/*` 与 `data/processed/orders.db`。
3. **不静默强转**：无法落进契约的行会被丢弃**并计数**，因为丢行会改变金额口径。
4. **每个数字可复跑**：报告里每个数都能用一条命令重现。

## 4. 数据源与网络实测

| 源 | URL | 实测结果 |
| --- | --- | --- |
| 主源：UCI Online Retail II（zip，内含 2 个 xlsx） | `https://archive.ics.uci.edu/static/public/502/online+retail+ii.zip` | HTTP 200；**站点极慢（实测 40.1 KB/s，1138 s 下完 45.6 MB）且不支持 Range 断点续传** |
| 备源：同零售商的 2010-2011 CSV 镜像 | `https://raw.githubusercontent.com/databricks/Spark-The-Definitive-Guide/master/data/retail-data/all/online-retail-dataset.csv` | HTTP 200，`Content-Length: 45,038,760`；已拉取 8.4 MB 抽样确认可读，主源成功后按需删除（未留存）；**按内容判重几乎全是重复行**（见报告 5.1 第 8 条） |

已实测不可用（均返回 `000`，连接被阻断）：`huggingface.co/datasets/*/resolve/main/*`。
`media.githubusercontent.com` 对同一文件返回 404（该仓库未启用 LFS 媒体路径）。

脚本会优先使用已存在的本地文件，不会重复下载：

```bash
# 1) 全链路（无本地文件时才下载）
.venv/Scripts/python.exe scripts/ingest_real_data.py

# 2) 复用已下载文件，跳过网络
.venv/Scripts/python.exe scripts/ingest_real_data.py --skip-download

# 3) 指定某个原始文件（脚本会自动识别 .zip / .xlsx / .csv）
.venv/Scripts/python.exe scripts/ingest_real_data.py --raw data/raw/online_retail_ii.zip

# 4) 强制重下
.venv/Scripts/python.exe scripts/ingest_real_data.py --force-download
```

> ⚠️ 主源 zip 约 45 MB，在实测网速下需要较长时间。脚本用 `--download-timeout`
> 控制超时（默认 1800 秒），不会无限挂起。

### 4.1 用外部工具下载时，如何让报告不说谎

若原始文件是用 `curl` / 浏览器等**外部工具**抓下来的，脚本无从得知耗时与速度。
此时不要留空，用 `--provenance-note` 把实测事实写进报告的表 1：

```bash
# 交互式 curl 的实测输出（HTTP 200, 45,622,418 字节, 1138.3 s, 40.1 KB/s）
.venv/Scripts/python.exe scripts/ingest_real_data.py \
  --provenance-note "本次下载由交互式 curl 完成（非本脚本）：HTTP 200，45,622,418 字节，耗时 1138.3 s，平均 40.1 KB/s"
```

报告表 1 的「下载旁证」行会原样引用这段话；「下载耗时/速度」行则显式写明
「本次运行未下载（脚本不掌握该数值）」，而不是打印一个假数字或 `n/a`。

## 5. 完整性校验

下载完成后先验真，再去解析——不要相信一个"看起来大小差不多"的文件：

```bash
# 归档完整性（必须输出 No errors detected）
unzip -t data/raw/online_retail_ii.zip | tail -3

# 本次实测值：45,622,418 字节 / 1 个成员 online_retail_II.xlsx
sha256sum data/raw/online_retail_ii.zip
# 572e36277c2390fbfde10664750731e0a86f55e33470d91919085f0408e67bfb
```

报告表 1 的字节数与 SHA-256 直接来自 `reports/real_data_stats.json`，
`--skip-download` 复跑时若这两项与首次不一致，说明原始文件被换过，报告数字不再可比。

> 注意：Online Retail II 是**一个 xlsx 里放两个年度工作表**（Year 2009-2010 / Year 2010-2011）。
> 只读第一个 sheet 会把数据量悄悄砍半（525,461 vs 合计 1,067,371），脚本因此对成员与
> 每个 sheet 的行数都单独计数。

## 6. 列映射契约

真实列 → `scripts/build_orders_db.py:COLUMNS` 声明的 14 列（完整表见报告的 §2）。
要点：

| 真实列 | 契约列 | 转换 |
| --- | --- | --- |
| `InvoiceNo` | `order_id` | `INV<sha1(InvoiceNo)[:10]>`；`C` 前缀语义转到 `status` |
| `CustomerID` | `customer_id` | `CUS<零填充 6 位>`；空值 → `CUS_UNKNOWN` |
| （无） | `merchant_id` | 常量 `MRC_REAL_01`（源里只有一家零售商） |
| `InvoiceDate` | `order_time` | 分钟精度，补 `+00:00`（源无时区） |
| （无） | `status` | 推导见 §6 |
| `StockCode` | `category` | `SKU_<StockCode>`（源无类目层级） |
| `Quantity` | `quantity` | 整数，负数保留 |
| `UnitPrice` | `unit_price_minor` | 英镑浮点 → 便士：`round(x * 100)` |
| （无） | `discount_minor` / `shipping_fee_minor` | 硬 0（源不记录） |
| `Quantity × UnitPrice` | `paid_amount_minor` / `refunded_amount_minor` | 正腿进 paid，负腿取绝对值进 refunded |
| （无） | `payment_method` / `source_channel` | 字面量 `unknown` |

**契约里 5 列在真实数据上只能填占位值**，这意味着真实数据不支持
「按渠道 / 支付方式 / 折扣 / 运费」的任何分析，报告里不得声称这类结论。

## 7. 状态映射（近似，必须标注）

真实数据**没有生命周期字段**。`status` 完全由两个信号推导：

| 条件 | 映射 |
| --- | --- |
| `InvoiceNo` 以 `C`/`c` 开头 | `cancelled` |
| 否则 `Quantity < 0` | `refunded` |
| 其余 | `completed` |

推论：真实库上 **`shipped` 恒为 0**，`pending` 也永远为空——这两个状态在源数据里
没有对应物。因此真实库的 `revenue` 口径实际上等于「所有非负数量、非取消行」，
与合成数据的 `completed + shipped` 语义只是**近似对齐**，不可直接对比金额。

`quantity > 0` 这个过滤条件（`src/agent/tools.py` 的 `MetricArguments.compile`）
本身就会把退货腿排除在金额口径之外，所以两边的处理是一致的。

## 8. 金额单位

| 项 | 合成数据 | 真实数据 |
| --- | --- | --- |
| 币种 | CNY | GBP |
| 存储 | 整数「分」 | 整数「便士」（由英镑浮点 `round(x*100)` 得到） |
| 展示 | `MetricTool` 除以 100 后输出 `revenue_yuan` | 同左，但**单位实际是英镑** |

本次**没有做汇率折算**：只是把「便士」当作最小货币单位复用了整数分的存储语义。
所以两边的人民币金额不可相加，报告里只做口径与结构对比。

精度验证：入库后 `paid_amount_minor - refunded_amount_minor != quantity * unit_price_minor`
的行数必须为 **0**（`reports/real_data_stats.json: project_caliber.cross_check_sqlite`）。
若该数不为 0，说明 `round()` 位置错了，脚本不会静默通过。

## 10. 常见问题

**Q：为什么入库行数和原始行数不一样？**
A：无法落进契约类型的行被丢弃并计数（`stats.normalization.rows_dropped_untypeable`）。
占比的分母始终是**原始行数**，报告会显式说明。

**Q：为什么不做去重？**
A：去重会改变金额合计。脚本保留重复行，只**计数**，把「是否去重」留给口径决策者，
并在报告里给出重复行的规模。

**Q：真实数据能替代合成数据吗？**
A：不能。真实数据没有 `status` 生命周期、没有渠道/支付/折扣/运费、币种也不同，
无法支撑 Agent 的完整评测集。它的价值是**压力测试口径**与**暴露合成数据的盲区**。

**Q：这条链路会改动 `config/data_spec.yaml` 吗？**
A：不会。报告只给出**改进建议**（应补哪几类真实异常），不修改配置。
